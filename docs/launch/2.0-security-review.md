# WeMoa 2.0.0 — 제출 전 보안·개인정보 점검

- 날짜: 2026-11-12 · 브랜치 `release/2.0-ios` · 읽기 전용 점검(코드 변경 없음)
- 범위: git 비밀값, 공유 링크(ADR-016) 암호화·서버·웹 보기, 백업 가져오기, app.json 개인정보/권한, 의존성, 심사 위험

## 결론: **고칠 것 있음** (막는 건 1건, 코드 밖 작업)

코드 쪽은 출시해도 됩니다. 암호화 설계(기기에서 AES-256-GCM, 링크마다 새 키, 키는 `#` 뒤에만), 웹 보기의 XSS 방어, CSP,
백업 가져오기 검증 모두 문제 없습니다. **다만 공개된 개인정보처리방침 페이지가 1.0 그대로라서** 2.0에 새로 생긴 서버 보관을 설명하지 않습니다.
이것만은 제출 전에 꼭 고쳐야 합니다. MED 2건(업로드 남용, Export Compliance 답변)은 오너가 정하면 됩니다.

## HIGH

### H1. 호스팅된 개인정보처리방침이 옛날 판(아마따, 공유 링크 설명 없음)
- 위치: `https://devlyo.github.io/amatta-legal/privacy-policy.html` (`docs/launch/app-store-metadata.md:72`의 ASC URL)
- 확인한 것(2026-11-12 curl): HTTP 200이지만 본문에 **"아마따" 6회**, **시행일 2026년 6월 30일**, "Vercel"·"공유 링크" **0회**.
  로컬에서 빌드한 `docs/legal/privacy-policy.html`과 `src/legal/legal-text.ts:35-38`에는 공유 링크 절이 들어 있음.
- 위험: 2.0은 사용자 콘텐츠(암호화본)를 서버에 보관하고 App Privacy 라벨도 "기타 사용자 콘텐츠"로 신고합니다. 그런데 공개 정책은
  "외부로 보내지 않음"이라고 되어 있어 Guideline 5.1.1(i)·5.1.2와 맞지 않고, 앱 이름도 다릅니다. → 리젝 사유가 될 수 있음.
- 고칠 것: `npm run legal:build` → `docs/legal/*.html`을 `devlyo/amatta-legal`에 올리기 → URL을 다시 열어
  "아마따" 0회, 시행일 = 출시일, "캘린더 공유 링크" 절이 있는지 확인. 지원 URL(`/amatta-legal/`) 첫 화면에 있는 이름도 같이 확인.

## MED

### M1. 인증 없는 업로드 API — 남용·비용·CSRF 방식 업로드
- 위치: `web/share/public/api/share.ts:7-21`, `api/_lib.ts:31-43`
- 현재: 본문 ≤ 32KB, base64url만, IP당 분당 20건. 하지만 이 제한은 **함수 인스턴스 메모리 안에서만** 동작해서
  인스턴스가 여러 개면 쉽게 넘깁니다. `Content-Type`·`Origin`을 확인하지 않아서, 아무 웹페이지나 방문자 브라우저로
  `text/plain` "simple request" POST를 보낼 수 있습니다(preflight 없이 저장되고, 응답만 못 읽음). 여러 IP로 퍼뜨리기 쉽습니다.
- 영향: 개인정보 유출은 없습니다(암호문만 저장하고, 키는 서버에 없음). 남는 위험은 ① 32KB짜리 14일 무료 파일 호스팅으로 악용,
  ② Blob 저장·작업 할당량이 다 차서 **공유 기능이 멈추거나 요금이 나옴**.
- 고칠 것(작은 것부터):
  1. `content-type`이 `application/json`이 아니면 415로 거절 → 다른 사이트의 브라우저 요청은 preflight를 거쳐야 하는데 CORS 헤더가 없어서 막힘.
     `Origin` 헤더가 있는데 자기 origin이 아니면 403(RN `fetch`는 보통 Origin을 안 보냄 — 기기에서 한 번 확인).
  2. Vercel Firewall에서 `POST /api/share`에 rate-limit 규칙 걸기(플랜에서 되면). Blob 사용량 알림·Spend Management 켜기.
  3. (선택) 앱 버전 헤더 같은 약한 표식 확인. 진짜 인증은 이 구조에서는 불가능하다는 점을 ADR-016에 남겨 두기.

### M2. `ITSAppUsesNonExemptEncryption = false` — 근거는 있지만 프랑스 배포는 따로 정해야 함
- 위치: `app.json` `ios.infoPlist`
- 판단: 앱이 직접 AES-256-GCM(`@noble/ciphers`)으로 사용자 데이터를 암호화합니다. 인증 전용이 아니고 OS 암호화도 아니라서
  엄밀히는 "암호화를 사용함"에 해당합니다. 다만 **표준 알고리즘 + 일반 소비자용 앱(EAR mass market, 5D992.c)**이라
  미국 수출 서류는 필요 없어서 `false`로 두는 건 업계에서 흔하고 근거도 있습니다. HTTPS는 OS가 처리하므로 면제입니다.
- 남은 위험: Apple 안내에 따르면 표준 암호화를 쓰는 앱을 **프랑스 스토어**에 내면 프랑스 수입 신고 서류가 필요합니다.
- 고칠 것: 배포 국가를 한국(+필요한 나라)으로 정하고 **프랑스는 빼기**, 또는 ASC 질문에 "표준 알고리즘 사용"으로 답하고 안내를 따르기.
  정한 내용을 `docs/launch/app-store-2.0.md`의 "암호화(Export Compliance)" 항목에 기록.

## 통과한 항목 (근거)

- **git 비밀값**: 추적되는 파일 중 `.env*`는 `.env.example`(비밀값 없음)뿐. 예전 `.env`(커밋 `c13f521`, `becd779`에서 추적 해제)에는
  `EXPO_NO_TELEMETRY=1`만 있었음. `web/share/public/.env.local`은 **추적 안 됨**(`web/share/public/.gitignore:2 .env*`, `.vercelignore`도 `.env*`).
  `.vercel/`도 무시됨. Blob/Vercel/Expo/GitHub/AWS 토큰 패턴과 `BEGIN … KEY`는 검색해도 0건. `*.p8/.p12/.mobileprovision/.pem/.key`는 무시 목록에 있고 추적 0건.
  추적되는 이메일은 공개 문의 주소뿐.
- **암호화** (`src/share/share-crypto.ts:33-41`): 키 32B와 nonce 12B 모두 `expo-crypto.getRandomBytes`(네이티브 CSPRNG,
  `secure-random.ts`)에서 뽑음. 링크마다 새 키라서 nonce가 겹칠 일이 없음. AES-GCM AEAD(태그 검증 실패 → `invalid`). 키는
  `fetch` 본문(`{c}`)과 URL path에 없고 `#` 뒤에만 있음(`:72`). 보기 페이지의 `fetch`는 `/api/share/<id>`만 부르고 `credentials:'omit'`.
  보기 페이지는 키 형식 `^[A-Za-z0-9_-]{20,64}$`를 확인하고, WebCrypto가 키 길이를 다시 검증함.
- **서버**: id = 편향 없는 base62 10자(약 59.5bit, `_lib.ts:20-29`), 읽을 때 `ID_RE`로 검증, `allowOverwrite:false`, private Blob.
  만료(TTL)는 저장할 때 `ttlDays:14`로 걸고, **읽을 때도 `uploadedAt`으로 14일을 다시 확인**(`[id].ts:13`). 오류 응답은
  `bad_request/not_found/unavailable`만 보내고 내부 오류는 서버 로그에만 남음. 응답 `no-store`. CORS 헤더 없음(다른 사이트는 응답을 못 읽음).
- **웹 보기** (`web/share/src/main.ts`): 사용자 문자열은 모두 `textContent`로 넣음, `innerHTML` 0건(번들 `app.js`에서도 0건).
  색·아바타는 상수 표에서 인덱스로만 고르고, 아바타 경로는 허용 목록으로 제한. `app.js`는 `main.ts`를 다시 빌드한 결과와 **바이트가 같음**.
  CSP `default-src 'none'; script/style/img/connect 'self'; frame-ancestors 'none'`, 인라인 스크립트 없음, 외부 요청 없음.
  `Referrer-Policy: no-referrer`·`X-Robots-Tag: noindex`·`nosniff`·HSTS preload(실제 응답 헤더로 확인). 잘못되거나 큰 데이터는
  `validWire`(`share-codec.ts:170-192`)에서 개수·인덱스·범위를 확인하고 JSON 길이도 제한함 → 안내 화면.
  `npx jest tests/share` 13/13 통과.
- **백업 가져오기**: JSON.parse를 try로 감쌈, 5MB 상한, 행마다 타입·범위·FK 검증, 쿼리는 전부 `?`로 값을 넘김(테이블 이름만 고정
  상수 `LEAF_FIRST`), 배타 트랜잭션 + `foreign_key_check`, 파일은 피커가 만든 cache 사본을 읽고 지움(경로 조작 없음).
- **설정/권한**: http:// 사용 0건(ATS 예외 없음). 캘린더 권한 문구("기기 밖으로 전송되지 않음")가 실제 동작과 맞음 — 공유
  페이로드는 SQLite 일정만 담고, 기기 캘린더 일정은 넣지 않음(`share-payload.ts`). Privacy manifest = OtherUserContent, linked=false,
  tracking=false, AppFunctionality → 정한 ASC 라벨과 같음. Tracking 도메인 없음. 앱 코드에 `console.log` 0건, `console.warn` 9건은
  오류 객체만 찍고 개인 데이터는 안 찍음.
- **옛 이름**: `src`·`app`·웹 보기에서 사용자에게 보이는 "아마따"는 0건(남은 건 주석·에셋 경로·번들 ID뿐 — 번들 ID는 ADR-011에 따라 유지).
